# site.js: behaviour

`site/assets/site.js` is the only script on the site: about 210 lines of plain JavaScript, with no libraries and no build step. It runs the theme switch, the typing prompt, the header hairline, the name that docks into the header, the minimap and a console greeting. Each of these is an extra – with JavaScript off, every page is still complete and readable, and this chapter shows how each part makes sure of that.

Figures marked "measured" come from a 1440 × 900 window in Chromium.

## Loading: two scripts, two moments

Before the first line of `site.js` runs, a smaller script has already done its part. Both are in `site/index.html`. The first is in `<head>`, the second just before `</body>`:

```html
<script>document.documentElement.classList.add('js');try{var t=localStorage.getItem('theme');if(t==='light'||t==='dark')document.documentElement.setAttribute('data-theme',t)}catch(e){}</script>
```

```html
<script src="assets/site.js" defer></script>
```

- **The boot script** is inline and has no `defer`, so it runs the moment the parser reaches it, before anything is painted. It does only the two things that must be in place for the first paint: the `js` class and a stored theme. If the theme were applied later, a visitor who chose dark would first see the light page flash up.
- It sits *before* the stylesheet `<link>` on purpose. An inline script that comes after a stylesheet that is still loading has to wait for it, because the script might ask for styles. Placed before the link, it runs at once.
- `defer` has no effect on inline scripts, which is another reason this code is synchronous and tiny.
- It uses old-style syntax (`var`, `catch(e)`) so that it runs in any browser. One side effect: a `var` at the top level of a classic script becomes a global, so `window.t` exists afterwards.
- **The main script** is external and uses `defer`. A classic script can be loaded in three ways:
  - no attribute – the parser stops at the tag, downloads and runs the file, then carries on building the page
  - `async` – downloads in parallel and runs as soon as it arrives, possibly before the document is fully parsed, and in no guaranteed order
  - `defer` – downloads in parallel and runs after the whole document has been parsed and the stylesheets have loaded, in document order, just before the `DOMContentLoaded` event
- At the end of `<body>` the DOM is almost complete anyway, so `defer` mostly makes the guarantee explicit. Every `querySelector` in the file will find its element, and the CSS is already applied when the script reads computed styles. You could move the tag into `<head>` without changing any code.

## The wrapper

```js
/* peterstieg.com – no tracking, no cookies, no framework. */
(() => {
```

```js
})();
```

- `() => { … }` is an arrow function. The parentheses around it make the parser read it as an expression, not a declaration.
- The `()` at the very end calls it straight away. This pattern is called an IIFE (immediately invoked function expression).
- **Why it is needed:** in a classic script, top-level `var`s and function declarations become properties of `window`. Top-level `const` and `let` do not, but all classic scripts on a page share one global scope, so two of them declaring the same name collide. Inside a function, every name is private.
- In this file that is a real risk, not a theoretical one. `window.top` is a built-in global that cannot be redeclared, so `const top = …` at the top level of a classic script throws `SyntaxError: Identifier 'top' has already been declared`, and none of the file would run. Inside the IIFE, `top` is a new local name that hides the global one.
- **Closure:** the event handlers created inside the IIFE keep access to its variables (`dist`, `mode`, `bars` …) for as long as the page is open, even though the outer function returned long ago. The downside is that the console cannot reach those variables (see Try it).
- `<script type="module">` would give the same private scope and is deferred automatically. A classic script with an IIFE has one practical advantage: it also runs when you open the HTML file straight from disk (`file://`), where Chromium refuses to load modules.

**`const` and `let`** – the file never uses `var`:

- `const` means the name can never be reassigned. Most names here are element references or functions that never change.
- `const` does not freeze objects. `pairs` is a `const`, yet `dockMeasure` writes `p.ox`, `p.k` and others onto the objects inside it.
- `let` is used for values that change: `dist`, `mode`, `bars`, `view`, `scale`, `i`, `dragging`, `raf`, `rt`. Unlike `var`, a `let` only exists inside the block `{ … }` where it is declared.
- A function stored as `const name = () => …` is not hoisted the way a `function name()` declaration is. Calling it before its line has run throws a ReferenceError; the period before that line is called the temporal dead zone. `build` calls `paint`, which is defined further down. That works because `build` only ever runs later, from events and promise callbacks, after the whole IIFE body has executed.

## Root, reduced motion, the `js` class

```js
  const root = document.documentElement;
  const reduce = window.matchMedia("(prefers-reduced-motion: reduce)").matches;
  root.classList.add("js");
```

- `root` is the `<html>` element. The theme attribute and the state classes (`js`, `typed`) go here, so CSS can match any element below them.
- `window.matchMedia(query)` evaluates a CSS media query from JavaScript and returns a `MediaQueryList` object. `.matches` is the yes/no answer at this moment.
- `prefers-reduced-motion: reduce` is true when the visitor has turned down animations in the operating system: "Reduce motion" on macOS and iOS, "Animation effects" off on Windows, "Remove animations" on Android.
- `reduce` drives three choices later on: no typing animation, a swap instead of a flight when docking, and no smooth scrolling on minimap clicks.
- Edge case: the value is read once and stored as a boolean. If the visitor changes the setting while the page is open, the script keeps the old answer until a reload, whereas the media queries in `site.css` react immediately. Compare `mqDark` below, which keeps the `MediaQueryList` object so it can listen for changes.
- `root.classList.add("js")` repeats what the boot script already did. `classList.add` ignores a class that is already there, so this line only matters on a page without the boot script.
- The CSS relies on the class:
  - `html:not(.js) .themes { display: none; }` hides theme buttons that would do nothing without JavaScript
  - `html:not(.js) .to-top` keeps the back-to-top button permanently visible
  - `.js .top.dock .home` hides the header logo only when the script is there to bring it back

## Theme

There are three states: no choice (follow the system), light and dark. The state lives in one attribute, `data-theme` on `<html>`, and is absent when no choice has been made. JavaScript never sets a colour itself. It sets the attribute, and the custom properties in `site.css` do the rest:

| `data-theme` | System setting | Matching rule in site.css | Result |
|---|---|---|---|
| absent | light | `:root` | light |
| absent | dark | `@media (prefers-color-scheme: dark)` → `:root:not([data-theme="light"])` | dark |
| `light` | dark | the `:not(…)` rule fails, only `:root` applies | light |
| `dark` | any | `:root[data-theme="dark"]` | dark |

### Constants and helpers

```js
  /* ---------- Theme: follows the system until the visitor picks one; the pick is remembered locally. */
  const mqDark = window.matchMedia("(prefers-color-scheme: dark)");
  const COLORS = { light: "#F7F6F3", dark: "#181A1C" };
  const stored = () => { try { return localStorage.getItem("theme"); } catch (_) { return null; } };
  const effective = () => root.getAttribute("data-theme") || (mqDark.matches ? "dark" : "light");
```

- `mqDark` keeps the `MediaQueryList` object itself, not just `.matches`. That gives two things: `mqDark.matches` is always current, and the object can fire `change` events.
- `COLORS` holds the browser interface colour for each theme – the address bar on mobile Safari and Chrome for Android. The values are the same as `--paper` in `site.css` and the two `<meta name="theme-color">` tags, so the same two colours are written in three places, and a new background colour means three edits.
- `stored()` returns whatever is saved under the key `"theme"`: `"light"`, `"dark"`, `null` if nothing is saved, or anything else someone put there.
- The `try … catch` is there because `localStorage` can throw:
  - `SecurityError` when the visitor has blocked site data or cookies for the site – even reading `window.localStorage` throws then
  - `SecurityError` inside a sandboxed iframe that is not same-origin
  - `QuotaExceededError` on `setItem` when storage is full; older Safari versions had zero quota in private mode, so every write failed
- Without the `catch`, one exception here would stop the whole IIFE: no typing, no docking, no minimap. With it, a failure just means "no stored choice".
- `catch (_)`: `_` is a name for an error that is not used. Since ES2019 a bare `catch { … }` does the same job.
- `effective()` returns the theme that is actually on screen. `getAttribute` returns `null` when the attribute is missing, and `||` then falls back to the system setting.

> **Mechanism – localStorage scope.** `localStorage` is a synchronous store of string key-value pairs, scoped *per origin* (scheme + host + port). Every page on `https://peterstieg.com` shares it – English, German, legal pages and 404 – so one click sets the theme across the whole site. It is not shared with `http://`, another subdomain or a copy opened from disk. It is also separate per browser and per browser profile, it is not synced between devices, and a private window starts empty and forgets everything when it closes. Unlike a cookie it is never sent to the server, so "no cookies" still holds. Entries never expire on their own, but the visitor can clear site data, and Safari may delete script-written storage for sites that have not been visited in seven days of browser use.

### paintTheme()

```js
  const paintTheme = () => {
    const now = effective();
    document.querySelectorAll("[data-theme-set]").forEach((b) =>
      b.setAttribute("aria-pressed", String(b.dataset.themeSet === now)));
    if (root.hasAttribute("data-theme")) {
      document.querySelectorAll('meta[name="theme-color"]').forEach((m) => m.setAttribute("content", COLORS[now]));
    }
  };
```

- "Paint" here means bringing the interface in line with the current state. The function never changes the theme itself.
- `querySelectorAll("[data-theme-set]")` is an attribute selector that finds the two theme buttons. It returns a static `NodeList`, which has `forEach`.
- `b.dataset.themeSet` reads the `data-theme-set` attribute. `dataset` exposes every `data-*` attribute as a property: it drops `data-` and turns each dash plus lowercase letter into an uppercase letter, so `data-theme-set` becomes `themeSet`. Values are always strings, and writing `b.dataset.x = "y"` creates `data-x="y"`.
- `aria-pressed` turns a `<button>` into a toggle button for assistive technology, which then announces it as "Dark, toggle button, pressed". `String(true)` gives `"true"`. `setAttribute` would convert the value anyway, but the explicit conversion shows what ends up in the HTML.
- The same attribute styles the active button: `.themes button[aria-pressed="true"]` in `site.css`. Because the state and the styling use the same attribute, they cannot get out of sync.
- When following the system, the button that matches the system theme shows as pressed. The buttons show what you see, not whether you made a choice.
- **theme-color:** the HTML has two meta tags, one with `media="(prefers-color-scheme: light)"` and one with the dark version, and the browser uses the one whose media query matches the *system* setting. That is only correct when the page follows the system. If the visitor picks dark on a light system, the browser would still use the light tag, and the address bar would stay light above a dark page. So when a choice exists, the script writes the chosen colour into *both* tags, and whichever one the browser picks is right.
- With no choice, the tags are left alone, so the browser keeps switching between them automatically.
- `'meta[name="theme-color"]'` uses single quotes outside and double quotes inside, which avoids escaping.

### Click handlers

```js
  document.querySelectorAll("[data-theme-set]").forEach((b) => b.addEventListener("click", () => {
    const val = b.dataset.themeSet;
    root.setAttribute("data-theme", val);
    try { localStorage.setItem("theme", val); } catch (_) { /* private mode: the choice lasts for this page */ }
    paintTheme();
  }));
```

- Each button gets its own listener. Through the closure, each listener remembers its own `b`.
- `click` fires for a mouse click, a tap and the keyboard (Enter or Space on a focused `<button>`). That is why the markup uses real `<button type="button">` elements and not clickable `<span>`s.
- `val` comes from the markup, so the HTML is the only place that says which button means which theme.
- `setAttribute("data-theme", val)`: the browser recalculates styles, the custom properties change, and the page switches theme without a reload.
- The `setItem` call is wrapped in `try … catch`. If storage fails, the attribute still applies to the current page view, and the next page simply loads without a saved choice.
- `paintTheme()` updates `aria-pressed` and the meta tags.
- Once a button has been clicked, there is no way back to "follow the system" except clearing site data. That is a design decision, not a bug.

### Startup and system changes

```js
  const s0 = stored();
  if ((s0 === "light" || s0 === "dark") && !root.hasAttribute("data-theme")) root.setAttribute("data-theme", s0);
  mqDark.addEventListener("change", paintTheme);
  paintTheme();
```

- Only the two known values are accepted. A stray value like `"blue"` would otherwise set `data-theme="blue"`: no CSS rule would match it, `effective()` would return `"blue"`, `COLORS["blue"]` would be `undefined`, and the meta tags would get `content="undefined"`.
- `!root.hasAttribute("data-theme")`: normally the boot script has already set the attribute, so this line does nothing. It is a fallback for a page without the boot script.
- `mqDark.addEventListener("change", paintTheme)` runs when the system switches between light and dark, for example with automatic dark mode at sunset. CSS updates itself through its media query; the script only needs to move `aria-pressed`. If a choice exists, `effective()` returns the same value as before, so the call changes nothing. The listener receives a `MediaQueryListEvent`, which `paintTheme` ignores.
- Edge case: `MediaQueryList.addEventListener` exists only from Safari 14 on. Older Safari had only `addListener`, so there this line would throw a TypeError and stop everything after it.
- The final `paintTheme()` sets the initial state. The markup ships `aria-pressed="false"` on both buttons.

### How the two scripts share the work

| Task | Boot script (`<head>`) | site.js (deferred) |
|---|---|---|
| `js` class | sets it | sets it again (no effect) |
| `data-theme` from storage | sets it | sets it only if missing |
| `aria-pressed` on buttons | – | sets it |
| `theme-color` meta tags | – | overrides them when a choice exists |
| Listeners (click, system change) | – | registers them |

The boot script does only what has to happen before the first paint. Everything else waits until the DOM is there. One consequence: for the fraction of a second between first paint and the deferred script, the browser's address bar can show the system colour while the page already shows the chosen theme.

## Typing prompt

```js
  /* ---------- Prompt: types the motto once. Full text stays in the HTML for no-JS and screen readers. */
  const cmd = document.querySelector(".hero .prompt .cmd");
  if (cmd) {
    const full = cmd.textContent;
    if (reduce) {
      root.classList.add("typed");
    } else {
      cmd.textContent = "";
      let i = 0;
      const step = () => {
        cmd.textContent = full.slice(0, ++i);
        if (i < full.length) setTimeout(step, 45 + Math.random() * 70);
        else root.classList.add("typed");
      };
      setTimeout(step, 600);
    }
  }
```

The markup it works on:

```html
<p class="prompt" lang="en"><span class="caret" aria-hidden="true">&gt;_</span><span class="cmd" aria-hidden="true">sudo dream plan ship</span><span class="sr-only">sudo dream plan ship</span><span class="cursor" aria-hidden="true"></span></p>
```

- The motto appears twice. `.cmd` is the visible copy and is hidden from assistive technology with `aria-hidden="true"`. `.sr-only` is the copy for screen readers.
- `.sr-only` in `site.css` shrinks the element to 1 × 1 px and clips it. It cannot be seen, but it stays in the accessibility tree. `display: none` or `visibility: hidden` would remove it from that tree as well.
- Result: a screen reader always reads one complete, unchanging sentence, and never a half-typed "sudo dre". Without JavaScript, `.cmd` simply shows the full text.
- `cmd` is `null` on pages without the prompt (legal pages, 404), and `if (cmd)` skips the whole block there.
- `full = cmd.textContent` saves the text of all text nodes inside the element before it gets cleared.
- **Reduced motion path:** nothing is animated, and `typed` (meaning "typing finished") is set at once. The CSS also limits the blink to `prefers-reduced-motion: no-preference`, so the same rule is enforced in two places.
- `cmd.textContent = ""` empties the span. Assigning `textContent` replaces all children with a single text node.
- `let i = 0` is the number of characters shown. It lives in the closure of `step`.
- `full.slice(0, ++i)`: `++i` adds 1 *first* and then uses the new value, so the first call shows `slice(0, 1)` = `"s"`. With `i++` the first call would show an empty string.
- `if (i < full.length)` schedules the next character after 45–115 ms. `Math.random()` returns a number from 0 up to (not including) 1, so `45 + Math.random() * 70` falls between 45 and 115.
- Otherwise the chain ends, and `typed` is added.
- `setTimeout(step, 600)` waits 0.6 s before the first character. With 20 characters at about 80 ms each, typing ends about 2.1 s after the script starts.

> **Mechanism – the event loop and a setTimeout chain.** JavaScript on a page runs on one main thread, one task at a time. `setTimeout(fn, ms)` does not pause anything. It asks the browser to queue `fn` as a new task after *at least* `ms` milliseconds, and in between the browser scrolls, renders and handles other events. Each `step` schedules the next one, so every delay can be different (the random part gives a human rhythm), and the chain stops simply by not scheduling another step. `setInterval` would use a fixed rhythm and would need `clearInterval` to stop. The delays are minimums: a busy thread runs the task later, and a background tab throttles timers to about one per second, so a hidden tab types slowly. That does no harm here.

The CSS reaction to `typed`:

```css
@media (prefers-reduced-motion: no-preference) {
  .typed .cursor { animation: blink 1.1s steps(2, start) 6; }
}
@keyframes blink { to { visibility: hidden; } }
```

The cursor blinks six times and then stays solid. The class goes on `<html>` because `.typed .cursor` only needs some ancestor to carry it.

## Header hairline

```js
  /* ---------- Header hairline once the page scrolls. */
  const top = document.querySelector(".top");
  const onScrollTop = () => top && top.classList.toggle("scrolled", window.scrollY > 8);
```

- `top` is the sticky `<header class="top">`. This is the name that would collide with `window.top` outside the IIFE.
- `top && …` short-circuits: if `top` is `null`, `&&` returns `null` and the right-hand side never runs.
- `classList.toggle(name, force)`: with a second argument, toggle means *set*. It adds the class when `force` is true and removes it when false. Without the second argument it would flip the class on every call.
- `window.scrollY > 8`: the 8 px threshold keeps the line from appearing for tiny offsets, such as iOS bounce or a restored scroll position of a few pixels.
- In CSS, `.top` always has `border-bottom: 1px solid transparent`, and `.top.scrolled` only changes its colour. Because the border always takes up space, the header never shifts by 1 px, and a colour change only needs a repaint, not a new layout.
- This line only defines the function. The scroll handler calls it, and so does the startup code (see Wiring).

## Docking

As you scroll, "PETER STIEG" and its `>_` fly from the hero into the header logo. The header has its own copy of the logo, which stays hidden during the flight. When the flight ends, the flying copy is hidden and the real logo is shown in the same place, so the name is never on screen twice. Position is computed from the scroll position, not from a timer, so scrolling back up plays the flight in reverse. This is called scrubbing.

### Setup

```js
  /* ---------- Docking: PETER STIEG and >_ travel from the hero into the header logo while scrolling.
     The name is visible exactly once. Scrubbed by scroll position, so scrolling up reverses it. */
  const hero = document.querySelector(".hero");
  const home = top && top.querySelector(".home");
  const pairs = hero && home ? [
    { src: hero.querySelector("h1"), dst: home.querySelector(".name") },
    { src: hero.querySelector(".prompt .caret"), dst: home.querySelector(".caret") },
  ].filter((p) => p.src && p.dst) : [];
  const fades = hero ? [...hero.querySelectorAll(".prompt .cmd, .prompt .cursor")] : [];
  let dist = 0, mode = "off";
```

- `hero` is `null` on the legal and 404 pages, and so is everything that depends on it.
- `home` uses the same guard: `&&` returns its first falsy operand, or else its last one.
- `pairs` uses `condition ? array : []`. Each pair has a `src`, which moves, and a `dst`, which is only measured as the target. The pairs are the hero `<h1>` → the header `.name`, and the hero prompt's `>_` → the header `.caret`.
- `.filter((p) => p.src && p.dst)` drops a pair if either element is missing. `dockMeasure` later needs exactly two.
- The comma after the second object is a trailing comma, which array literals allow.
- `fades` are the motto and the cursor, which fade out during the flight. `[...NodeList]` spreads the list into a real `Array`. A `NodeList` has `forEach` but none of the other array methods.
- `let dist = 0, mode = "off"` declares two variables in one statement. `dist` is the scroll distance over which the flight happens. `mode` is `"off"` (not measured or not possible), `"fly"` or `"swap"`.

The CSS hooks:

```css
.js .top.dock .home { visibility: hidden; }
.js .top.dock.docked .home { visibility: visible; }
.hero h1, .hero .prompt .caret { position: relative; z-index: 6; transform-origin: 0 0; }
.hero.flying h1, .hero.flying .prompt .caret { will-change: transform; }
.hero.docked h1, .hero.docked .prompt .caret { visibility: hidden; }
```

- The header logo is hidden while the header has `dock` but not yet `docked`.
- `visibility: hidden` is used rather than `display: none` because the element keeps its box, so the script can still measure where the target is. A hidden element also drops out of the tab order and the accessibility tree.
- `z-index: 6` (the header has 5) draws the flying name *over* the sticky header.
- `docked` on the hero hides the flown copies. `.top.docked ~ .to-top` also brings in the back-to-top button.

### textRects()

```js
  const textRects = (el) => {
    const r = document.createRange();
    r.selectNodeContents(el);
    return [...r.getClientRects()].filter((x) => x.width && x.height);
  };
```

- A `Range` is a stretch of document content between two boundary points. Under the hood, a text selection is one. `createRange()` creates an empty one.
- `selectNodeContents(el)` makes the range cover everything *inside* `el`, from before its first child to after its last child, but not `el` itself.
- `getClientRects()` returns a list of rectangles in viewport coordinates: one per line for every text fragment in the range, plus the border box of every element fully inside it. One line of text gives one rectangle. Text wrapped over two lines gives two.
- `[...]` turns the `DOMRectList` into an array, and `filter` drops zero-size rectangles, for example from empty or collapsed whitespace nodes.

**Why text rectangles and not the element box** (`getBoundingClientRect()`):

- **Width:** the `<h1>` is a block element, as wide as its column (measured: 952 px), while the text inside is much narrower.
- **Height:** an element's box height comes from `line-height`. The hero `<h1>` has `line-height: 0.98`, while the header logo inherits 1.55. A text rectangle's height comes from the font's ascent and descent – the font's height above and below the baseline – so it is proportional to font size regardless of line-height. Comparing text heights therefore gives the true size ratio (measured: 20 / 114 ≈ 0.175, which matches 16 px versus 92 px). The ratio of the two boxes would be off by a factor of about 1.6.
- **Offset:** with `line-height: 0.98`, the letters stick out above the `<h1>` box (measured: 12 px), and only the text rectangle shows that.
- **Wrapping:** the number of rectangles shows whether the name has wrapped onto two lines.

### ease()

```js
  const ease = (x) => (x < 0.5 ? 4 * x * x * x : 1 - Math.pow(-2 * x + 2, 3) / 2);
```

- It takes linear progress from 0 to 1 and returns eased progress from 0 to 1. This curve is known as cubic ease-in-out (`easeInOutCubic`).
- **First half:** `4x³` starts flat (slope 0) and speeds up. At 0.5 it reaches 0.5.
- **Second half:** with `u = 1 − x` (the distance still to go), `(−2x + 2)³ / 2` = `(2u)³ / 2` = `4u³`, so the formula is `1 − 4u³`. That is the first half mirrored, slowing to a halt at 1.
- Both halves meet at (0.5, 0.5) with the same slope of 3, so the curve has no kink.
- Values: 0 → 0 · 0.25 → 0.0625 · 0.5 → 0.5 · 0.75 → 0.9375 · 1 → 1.
- The effect: the name barely moves at first, covers most of the distance in the middle, and settles gently into the logo.

### dockClear()

```js
  const dockClear = () => {
    pairs.forEach((p) => { p.src.style.transform = ""; p.src.style.transformOrigin = ""; });
    fades.forEach((f) => { f.style.opacity = ""; });
  };
```

- `el.style` is the element's inline `style` attribute. Setting a property to `""` removes that declaration, so the stylesheet value applies again: no transform, `transform-origin: 0 0` from `site.css`, and full opacity.
- **Why this is needed:** `getBoundingClientRect` and `getClientRects` return positions *after* transforms. Measuring a name mid-flight gives you where it is drawn, not where it sits in the layout. `dockMeasure` and the minimap both need the layout position, so they clear transforms first.

### dockMeasure()

```js
  const dockMeasure = () => {
    if (pairs.length !== 2) return;
    top.classList.add("dock");
    dockClear();
    const sy = window.scrollY;
    const headerBottom = top.getBoundingClientRect().bottom;
    mode = reduce ? "swap" : "fly";
    for (const p of pairs) {
      const sr = textRects(p.src), dr = textRects(p.dst);
      if (sr.length !== 1 || dr.length !== 1) { mode = "swap"; }
      const a = sr[0] || p.src.getBoundingClientRect(), b = dr[0] || p.dst.getBoundingClientRect();
      const box = p.src.getBoundingClientRect();
      p.ox = a.left - box.left; p.oy = a.top - box.top;      // text origin inside the element box
      p.x0 = a.left; p.y0 = a.top + sy;                       // document coordinates
      p.x1 = b.left; p.y1 = b.top;                            // screen coordinates (sticky header)
      p.k = b.height / a.height;
      p.bottom = a.bottom + sy;
    }
    const name = pairs[0];
    dist = Math.min(400, Math.max(120, name.y0 - headerBottom + 40));
    if (mode === "swap") dist = Math.max(0, name.bottom - headerBottom);
  };
```

Two coordinate systems are involved:

- **Viewport (screen) coordinates** start at the top-left corner of the visible area. `getBoundingClientRect`, `getClientRects` and `clientY` use them.
- **Document coordinates** start at the top of the page. Document y = viewport y + `scrollY`.

Line by line:

- `if (pairs.length !== 2) return;` – both pairs are required. Otherwise `mode` stays `"off"`, `dockApply` does nothing, and the header logo stays a normal, visible logo, because `dock` is never added.
- `top.classList.add("dock")` switches on the CSS that hides the header logo. It is added here and not earlier so that, if measuring never happens, the logo stays visible. Because the logo is hidden with `visibility`, it can still be measured.
- `dockClear()` brings everything back to its layout position.
- `sy` is how many pixels of the document are scrolled above the top of the viewport.
- `headerBottom` is the viewport y of the header's bottom edge. The header is sticky at the top, so this value is the same at any scroll position (measured: 57 px – a 3.5rem minimum height plus the 1 px border).
- `mode = reduce ? "swap" : "fly"` sets the default mode.
- `for (const p of pairs)` – `for…of` loops over the values of any iterable.
- If the source or the target does not have exactly one text rectangle, the mode becomes `"swap"`. In practice that means the name has wrapped: at 320 px wide, "PETER STIEG" breaks onto two lines, and two lines cannot fly into a one-line logo.
- `a = sr[0] || p.src.getBoundingClientRect()`: if there is no text rectangle, the element box is used instead so the calculation does not crash. The mode is already `"swap"` in that case.
- `box` is the source element's border box.
- `ox`, `oy` locate the text's top-left corner inside that box (measured for the name: 0 and −12). This point becomes the `transform-origin` – the fixed point when scaling – and `transform-origin` is measured from the top-left of the border box, so the script converts the text corner into that frame.
- `x0`, `y0` are where the text starts. Adding `sy` turns `y0` into a document coordinate: the hero scrolls with the page, so its document position never changes. That also makes the measurement correct when the page loads already scrolled, after a reload or from an anchor link.
- `x1`, `y1` are the target in viewport coordinates, with no `+ sy`. The header is sticky, so on screen the target stays in the same place at any scroll position.
- `k = b.height / a.height` is the scale factor. Measured: 0.175 for the name, 0.8 for the caret.
- `p.bottom` is the document y of the text's bottom edge. Only swap mode uses it.
- The script adds new properties to plain objects. Objects are open to that, and the `const` on `pairs` does not prevent it.
- `dist = Math.min(400, Math.max(120, v))` is the usual clamp idiom: the inner `max` raises `v` to at least 120, and the outer `min` caps it at 400.
- `name.y0 − headerBottom` is how far the name's top sits below the header's bottom at scroll 0, which is roughly the scroll needed to bring the name up to the header. `+ 40` adds a little extra travel. The minimum of 120 keeps the flight from feeling abrupt, and the maximum of 400 keeps it from dragging. Measured: 162 − 57 + 40 = 145.
- **Swap mode:** `dist` becomes the scroll position at which the name's bottom edge reaches the header's bottom edge, meaning the name has passed completely under the header line. At that point the logo appears. `max(0, …)` guards against negative values. Measured with reduced motion: 276 − 57 = 219.
- These lines mix document y values with the viewport value `headerBottom`. That works because at scroll 0 the two systems coincide, and the sticky header sits where it sits at scroll 0.

> **Mechanism – forced layout (reflow).** The browser normally computes layout lazily, once per frame, just before painting. `getBoundingClientRect`, `getClientRects`, `scrollHeight`, `clientHeight` and, in Chromium, `scrollY` all need up-to-date geometry. If anything has changed since the last layout (here: the class just added and the inline styles just cleared), the browser has to recalculate styles and layout synchronously, on the spot. The cost grows with the size of the page. The rule is to write first and read afterwards: `dockMeasure` makes its two writes and then only reads. Alternating writes and reads in a loop forces a full layout on every pass, which is called layout thrashing. `dockMeasure` runs only at startup and on resize, never on scroll.

### dockApply()

```js
  const dockApply = () => {
    if (mode === "off") return;
    const sy = window.scrollY;
    const done = sy >= dist;
    top.classList.toggle("docked", done);
    if (mode === "swap") return;
    hero.classList.toggle("docked", done);
    const q = ease(Math.min(1, Math.max(0, sy / dist)));
    hero.classList.toggle("flying", q > 0 && !done);
    for (const p of pairs) {
      const dx = (p.x1 - p.x0) * q;
      const dy = (p.y1 - p.y0) * q + sy;
      const sc = 1 + (p.k - 1) * q;
      p.src.style.transformOrigin = `${p.ox}px ${p.oy}px`;
      p.src.style.transform = q ? `translate(${dx}px, ${dy}px) scale(${sc})` : "";
    }
    const o = Math.max(0, 1 - q * 1.8);
    fades.forEach((f) => { f.style.opacity = q ? String(o) : ""; });
  };
```

- `if (mode === "off") return;` – nothing has been measured yet, or docking is not possible on this page.
- `done` is true once the scroll has reached the end of the flight.
- `top.classList.toggle("docked", done)` shows the header logo (and the back-to-top button) once done. This runs in both modes.
- **Swap mode stops here:** no transforms and no fading. The hero name scrolls away normally, and the logo appears once the name has passed under the header line.
- Edge case: the hero `<h1>` keeps `z-index: 6` in swap mode too, so it slides *over* the sticky header instead of under it. For a short stretch you can see the large name and the logo at once. The same happens with JavaScript off, because that CSS rule does not depend on the `js` class.
- Edge case: swap mode never touches the hero's classes. If the window shrinks from "fly" to "swap" (wide → 320 px) while `hero.docked` is set, the class stays. Scrolled back to the top, the `<h1>` is still hidden, and so is the header logo.
- `hero.classList.toggle("docked", done)` hides the flown copies once the real logo takes over. `visibility: hidden` also removes the `<h1>` from the accessibility tree while the page is scrolled past `dist`.
- `q = ease(clamp(sy / dist, 0, 1))` gives eased progress from 0 to 1. The lower clamp matters on iOS, where pulling past the top gives a negative `scrollY`. In fly mode `dist` is at least 120, so the division is never by zero.
- `flying` turns on `will-change: transform` only during the flight. It tells the browser to prepare a separate compositor layer in advance, and removing the class at rest frees that layer's GPU memory.
- `dx`, `dy`, `sc` are each a linear interpolation (lerp): `start + (end − start) × q`. For the translation, start is 0 and end is the full offset. For the scale, start is 1 and end is `k`.
- **Why `dy` has `+ sy`:** the element sits in the document, so scrolling by `sy` moves it up the screen by `sy`. Without a transform its screen y is `y0 − sy`, but the target screen y is `y0 + (y1 − y0) × q`. The translation needed is the difference: `(y1 − y0) × q + sy`. The `+ sy` cancels the scroll, and the rest moves the text along its path. `dx` has no such term because the page does not scroll sideways.
- `transformOrigin` is set on every call (`${…}` is template-literal interpolation). It is cheap, and it has to be set again after `dockClear` removes it.
- `translate(dx, dy) scale(sc)`: CSS applies the functions from right to left. The element is first scaled around `transform-origin` – the text's top-left corner stays put – and then moved by `(dx, dy)`. Because the origin *is* the text's corner, the corner lands exactly on the interpolated point at any scale. With the stylesheet's origin `0 0` (the box corner) and `oy = −12`, the text would end up about 12 × (1 − 0.175) ≈ 10 px off.
- `q ? … : ""`: at q = 0 the transform is removed entirely, so the element is back in normal layout with no extra layer.
- After `done`, the transform keeps updating. The hidden copy stays parked over the logo, which has no visible effect.
- `o = max(0, 1 − 1.8q)` fades the motto and cursor out, reaching 0 at q ≈ 0.56, so they are gone before the name arrives. Style values are strings, hence `String(o)`, and `""` gives the stylesheet back control at q = 0.

> **Mechanism – transforms versus layout properties.** Rendering runs in stages: style → layout (the geometry of every box) → paint (pixels into layers) → composite (layers combined, usually on the GPU). Animating `top`, `left` or `font-size` changes geometry, so every frame needs layout for the element and possibly everything after it, followed by a repaint. `transform` and `opacity` skip layout: the element keeps its layout box, so its neighbours do not move and the hero does not collapse when the name leaves. The compositor just moves, scales and fades a layer that is already painted. That is why the flight stays smooth, and also why measuring needs `dockClear` – the layout box never moved, only the drawing did. A scaled layer can look slightly soft in mid-flight, but at the end the real header text takes over, so the logo at rest is always sharp.

### Worked example

Round numbers close to the measured ones: the name's text starts at `x0 = 200`, `y0 = 160` (document). The header name sits at `x1 = 224`, `y1 = 18`. The text heights are 100 and 18, so `k = 0.18`. The header bottom is at 60, so `dist = clamp(160 − 60 + 40) = 140`.

Set-up values: `x1 − x0 = 24`, `y1 − y0 = −142`, `k − 1 = −0.82`.

| scrollY | sy / dist | q | dx | dy = −142·q + sy | sc | text top on screen = 160 − sy + dy |
|---|---|---|---|---|---|---|
| 0 | 0 | 0 | – | – (transform removed) | 1 | 160 |
| 35 | 0.25 | 0.0625 | 1.5 | −8.9 + 35 = 26.1 | 0.949 | 151.1 |
| 70 | 0.5 | 0.5 | 12 | −71 + 70 = −1 | 0.59 | 89 |
| 105 | 0.75 | 0.9375 | 22.5 | −133.1 + 105 = −28.1 | 0.231 | 26.9 |
| 140 | 1 | 1 | 24 | −142 + 140 = −2 | 0.18 | 18 → `docked` |

How to read it:

- At 35 px of scroll the text has risen only 8.9 px on screen. The transform pushes it *down* by 26 px to cancel most of the scroll. That is the ease-in: the name holds its place.
- At the halfway point, `dy` is almost zero, because the scroll alone has done nearly all of the vertical travel the curve calls for.
- At 140 px the text's top-left corner sits at (224, 18) at 18 % size, exactly over the header's own copy. Then the classes swap, and nothing on screen changes.
- Motto opacity per row is `1 − 1.8q`: 1 · 0.89 · 0.1 · 0 · 0.
- The caret uses the same `q` but starts much lower (measured y0 = 387), so it covers more than twice the distance in the same 145 px of scroll and travels faster.

## Minimap

### Setup

```js
  /* ---------- Minimap: the page drawn as code lines, like the LinkedIn banner – click or drag to navigate. */
  const rail = document.querySelector(".minimap");
  const main = document.querySelector("main");
  let bars = [], view = null, scale = 1;
```

- `rail` is the empty `<div class="minimap" aria-hidden="true">` in the markup. The script fills it entirely. It is `aria-hidden` because it only repeats the page visually.
- The CSS shows it only on screens at least 74rem wide and 30rem tall: `position: fixed` on the right, `top: 5rem`, `bottom: 5.25rem`, `width: 4.25rem` and `touch-action: none`.
- `bars` holds `{ el, y }` for every bar. `view` is the box marking the viewport. `scale` is rail pixels per document pixel.

### build(): measuring

```js
  const build = () => {
    if (!rail || !main) return;
    rail.replaceChildren();
    bars = [];
    if (getComputedStyle(rail).display === "none") return;

    const docH = root.scrollHeight;
    const H = rail.clientHeight, W = rail.clientWidth;
    scale = H / docH;
    const box = main.getBoundingClientRect();
    const frag = document.createDocumentFragment();
```

- `replaceChildren()` with no arguments removes every child. `build` runs several times (twice at startup, then after every resize), so each run starts from an empty rail.
- `getComputedStyle(rail).display` reads the value the CSS actually applies. The media query in `site.css` decides whether there is a minimap, and the script follows it, so the breakpoint is defined in one place only. On phones, `build` stops here.
- `root.scrollHeight` is the full height of the document, including everything scrolled out of view (measured: 6243 px).
- `clientHeight` and `clientWidth` are the rail's inner size (measured: 736 × 68).
- `scale = H / docH` squeezes the whole page into the rail's height (measured: 736 / 6243 ≈ 0.118). Any document y times `scale` gives the matching rail y.
- `box` is the horizontal reference. `main` spans the viewport width, and bar x positions are proportions of that width, so the bars keep the page's left/right layout.
- A `DocumentFragment` is a lightweight container that is not part of the document. Adding bars to it does not touch the live page, so nothing is invalidated while the loop below is still reading geometry. At the end, one `appendChild` moves all of them in at once.

### build(): one bar per rendered line

```js
    const SEL = "h1, h2, h3, h4, p, li, dt, dd";
    main.querySelectorAll(SEL).forEach((el) => {
      if (el.querySelector(SEL)) return;              // leaf text blocks only
      if (!el.textContent.trim()) return;
      const range = document.createRange();
      range.selectNodeContents(el);
      const lines = [];                               // one bar per rendered line
      for (const r of range.getClientRects()) {
        if (!r.width || !r.height) continue;
        const l = lines.find((x) => Math.abs(x.top - r.top) < r.height / 2);
        if (l) { l.left = Math.min(l.left, r.left); l.right = Math.max(l.right, r.right); l.h = Math.max(l.h, r.height); }
        else lines.push({ top: r.top, left: r.left, right: r.right, h: r.height });
      }
      const isHead = /^H[12]$/.test(el.tagName);
      for (const l of lines) {
        const x = Math.max(0, ((l.left - box.left) / box.width) * W);
        const w = Math.max(3, ((l.right - l.left) / box.width) * W);
        const y = (l.top + window.scrollY + l.h / 2) * scale;
        const thick = Math.max(2, Math.min(isHead ? 7 : 3, l.h * scale * 0.55));
        const b = document.createElement("span");
        b.className = "mm-bar" + (isHead ? " h" : "");
        b.style.cssText = `top:${(y - thick / 2).toFixed(1)}px;left:${x.toFixed(1)}px;width:${Math.min(W - x, w).toFixed(1)}px;height:${thick.toFixed(1)}px`;
        frag.appendChild(b);
        bars.push({ el: b, y });
      }
    });
```

- `SEL` lists the block elements that contain text. `querySelectorAll` returns matches in document order.
- `if (el.querySelector(SEL)) return;` – inside a `forEach` callback, `return` works like `continue`. Only *leaf* blocks are used: an Experience `<li>` contains a `<p>` and an `<h3>`, so the `<li>` is skipped and its children draw the bars. Otherwise every line would be drawn twice. Text sitting directly in a non-leaf element next to a nested block would get no bar, but the current markup has no such case.
- `textContent.trim()` skips elements that are empty or contain only whitespace.
- The range works the same way as in `textRects`, but here several rectangles per element are expected.
- `for…of` works directly on the `DOMRectList`, which is iterable.
- **Why merge:** one visual line produces several rectangles – one per text node, plus the border box *and* the text of every inline element. `<li><span class="k">Scope</span> marketing, …</li>` gives three on its first line: the span's box, the span's text and the text after it.
- `lines.find(...)` treats a rectangle as part of an existing line when the tops are within half the rectangle's height of each other. A matching line is widened (`left` = min, `right` = max, `h` = max). Otherwise a new line starts.
- `/^H[12]$/.test(el.tagName)`: `tagName` is uppercase for HTML elements. Only `h1` and `h2` count as headings, and they are drawn thicker and darker (`.mm-bar.h`).
- `x` is the line's horizontal position as a fraction of `main`'s width, converted to rail pixels. `max(0, …)` clamps it at the left edge.
- `w` is the width, with a minimum of 3 px so short lines stay visible.
- `y` is the line's vertical centre: viewport y + `scrollY` gives the document y, `+ l.h / 2` moves to the centre, and `× scale` converts to the rail.
- `thick` is 55 % of the scaled line height, which roughly matches the ratio of letters to line spacing. It is clamped between 2 px (so it stays visible) and 3 px for text or 7 px for headings. At scale 0.118, a 25 px text line gives 1.6, which becomes 2, and the 114 px hero name gives 7.4, which becomes 7.
- `style.cssText` sets the whole inline style from one string, replacing anything that was there. `toFixed(1)` rounds to 0.1 px and returns a string. `Math.min(W − x, w)` stops the bar at the rail's right edge. `top` is the centre minus half the thickness.
- `bars.push({ el: b, y })` keeps each bar's centre for `paint`.
- Example: scale 0.12, a line at viewport y 300 while `scrollY` is 1000, height 25 → document centre 1312.5 → rail y 157.5 → thickness 1.65, raised to 2 → `top: 156.5px`.
- Edge case: `<h2>`s are `position: sticky` from 48rem up. A sticky element reports its *stuck* position, so if `build` runs while the page is scrolled (a resize mid-page, or a reload that restores the scroll position), the heading bars of the current section and of every section above it are drawn at the bottom of their sections instead of the top.
- Edge case: the `.sr-only` copy in the prompt is clipped but still laid out, so its text rectangle joins the prompt's line and makes that bar about twice as wide as the visible text.

### build(): finishing

```js
    view = document.createElement("span");
    view.className = "mm-view";
    frag.appendChild(view);
    rail.appendChild(frag);
    paint();
  };
```

- The viewport box is added last, so it is drawn on top of the bars (among positioned siblings, later ones paint over earlier ones). Its CSS includes `pointer-events: none`, so clicks pass through it to the rail.
- `rail.appendChild(frag)` moves the fragment's children into the rail in a single DOM insertion and leaves the fragment empty.
- `paint()` positions the viewport box straight away.

### paint()

```js
  const paint = () => {
    if (!view) return;
    const t = window.scrollY * scale, h = window.innerHeight * scale;
    view.style.top = t + "px";
    view.style.height = h + "px";
    for (const b of bars) b.el.classList.toggle("lit", b.y >= t && b.y <= t + h);
  };
```

- `view` is `null` until the first `build`, and stays `null` where there is no minimap.
- `t` is the viewport's top in rail coordinates, and `h` is its height (900 × 0.12 = 108 px).
- `"px"` is added because style values are strings with units.
- A bar is `lit` when its centre lies inside the viewport box – those are the lines currently on screen.
- `classList.toggle` with `force` changes nothing if the class is already in the right state, and causes no style work. Calling it for 160 bars per frame is cheap.
- `paint` runs on every scroll frame and reads only `scrollY` and `innerHeight`. `build` has already computed everything else: measure rarely, apply often.
- Minor: when a resize hides the minimap, `build` empties the rail but leaves `view` pointing at the old, now detached span. `paint` keeps updating that span, which is harmless.

### jump() and pointer handling

```js
  const jump = (clientY, smooth) => {
    const r = rail.getBoundingClientRect();
    const y = (clientY - r.top) / scale - window.innerHeight / 2;
    window.scrollTo({ top: Math.max(0, y), behavior: smooth && !reduce ? "smooth" : "auto" });
  };
```

- `clientY − r.top` is the pointer's y inside the rail. Dividing by `scale` gives the document y, and subtracting half the viewport height centres that point on screen instead of putting it at the top edge.
- Example: a click 300 px below the rail's top at scale 0.12 → document y 2500 → with a 900 px viewport, scroll to 2050.
- `scrollTo` takes an options object. `Math.max(0, y)` prevents negative values. No upper limit is needed, because the browser clamps scrolling to the maximum by itself.
- `behavior`: smooth for a click, without smoothing for a drag, and never smooth with reduced motion.
- Edge case: `"auto"` does not mean instant. It means "use the CSS `scroll-behavior`", and `site.css` sets `html { scroll-behavior: smooth; }` when motion is allowed. Measured: right after `scrollTo({ top: 1500, behavior: "auto" })`, `scrollY` is still 0. So drags are smooth-scrolled as well. `"instant"` would skip the animation.

```js
  if (rail) {
    let dragging = false;
    rail.addEventListener("pointerdown", (e) => { dragging = true; rail.setPointerCapture(e.pointerId); jump(e.clientY, true); });
    rail.addEventListener("pointermove", (e) => { if (dragging) jump(e.clientY, false); });
    rail.addEventListener("pointerup", () => { dragging = false; });
    rail.addEventListener("pointercancel", () => { dragging = false; });
  }
```

- Pointer events are one event model for mouse, touch and pen, so a single set of handlers covers all three.
- `let dragging` exists only inside the `if (rail)` block (block scope). The four handlers share it through their closures.
- `pointerdown` starts the drag, captures the pointer and jumps smoothly.
- `setPointerCapture(e.pointerId)`: `pointerId` identifies this one finger or this mouse. While it is captured, all of its events go to the rail even when the pointer leaves it, so a drag past the rail's edge keeps working, and `pointerup` still arrives when the button is released elsewhere. The capture ends automatically after `pointerup`.
- `pointermove` also fires for a mouse that is just hovering, which is why `dragging` decides whether to act.
- `pointercancel` fires when the browser takes the pointer over – for example when a touch turns into a scroll or zoom gesture, or the system interrupts. `touch-action: none` on the rail stops the browser from panning, so touch drags stay with the script.
- Minor: `pointerdown` reacts to any mouse button, including a right-click.

## Wiring

### layout()

```js
  /* ---------- Wiring */
  const layout = () => { dockMeasure(); build(); dockApply(); };
```

The order matters:

1. `dockMeasure` clears the transforms and measures the docking geometry.
2. `build` measures the text of all of `main`, including the hero name and caret. Text rectangles include transforms, so if `build` ran after `dockApply`, the minimap would draw the name's bar wherever it is mid-flight.
3. `dockApply` puts the transforms back for the current scroll position, using the new measurements.

### Scroll: throttled with requestAnimationFrame

```js
  let raf = 0;
  window.addEventListener("scroll", () => {
    if (raf) return;
    raf = requestAnimationFrame(() => { raf = 0; paint(); onScrollTop(); dockApply(); });
  }, { passive: true });
```

- `raf = 0` means "no frame scheduled". `requestAnimationFrame` returns a positive integer ID and never 0, so the ID doubles as a flag.
- If a frame is already scheduled, further scroll events are ignored. The callback first sets `raf` back to 0, so the next scroll can schedule the next frame, and then runs the three updates. All three only write to the page; the expensive measuring has already been done.

> **Mechanism – requestAnimationFrame.** The browser draws a new frame typically 60 to 120 times a second. Before each frame it handles pending scroll and resize events, runs the `requestAnimationFrame` callbacks, and then does style, layout, paint and composite. A rAF callback therefore runs right before the next frame, its changes appear in that frame, and the page is never updated more often than the screen refreshes. rAF also pauses in background tabs. Modern browsers already fire `scroll` about once per frame, but that is not guaranteed everywhere, and the guard costs nothing.

- `{ passive: true }` promises the browser that the listener will never call `preventDefault()`. This matters for `touchstart`, `touchmove` and `wheel`, which can cancel scrolling: without the promise, the browser has to wait for the handler before it can scroll. A `scroll` event cannot be cancelled – it fires after the scrolling has happened – so here the flag changes nothing. It documents intent and does no harm.
- Minor: `paint`, `onScrollTop` and `dockApply` each read `window.scrollY` themselves, after the previous one has changed classes. In Chromium that read can force a pending style update. It is cheap here, but reading `scrollY` once per frame and passing it down would be the stricter pattern.

### Resize: debounced with setTimeout

```js
  let rt = 0;
  window.addEventListener("resize", () => { clearTimeout(rt); rt = setTimeout(layout, 150); });
```

- Each resize event cancels the pending timer and starts a new one, so `layout` runs once, 150 ms after the *last* resize event. `clearTimeout` on an ID that has already fired, or on 0, does nothing.
- Dragging a window edge fires dozens of events. `layout` is expensive (hundreds of `getClientRects` calls plus a DOM rebuild), and the sizes in between do not matter.
- While a resize is in progress, the old measurements remain in use, so the flight can be briefly out of place until `layout` runs.
- On phones, `resize` also fires when the address bar collapses (`innerHeight` changes) and when the device rotates.

| | Throttle (scroll) | Debounce (resize) |
|---|---|---|
| Runs | at most once per interval, *during* the burst | once, *after* the burst has stopped |
| Tool here | `requestAnimationFrame` | `setTimeout` + `clearTimeout` |
| Suits | continuous visual feedback | expensive work that only needs the final state |

### Startup

```js
  onScrollTop();
  (document.fonts ? document.fonts.ready : Promise.resolve()).then(layout);
  window.addEventListener("load", layout);
```

- `onScrollTop()` runs straight away because the page may already be scrolled (after a reload, or when arriving via an anchor link), and the hairline should not wait for the first scroll.
- `layout` does not run straight away, because of fonts. `site.css` uses `font-display: swap`, so text first appears in a fallback font (`system-ui`) and is swapped for Atkinson Hyperlegible once it loads. The two fonts have different widths and heights, so anything measured before the swap is wrong.
- `document.fonts` is the `FontFaceSet` from the CSS Font Loading API. `.ready` is a Promise that resolves when pending font loads have finished.
- `.then(layout)` runs `layout` as a microtask once the promise resolves. Microtasks run as soon as the current task ends, before the next frame.
- In browsers without the API, `Promise.resolve()` is already resolved, so `layout` runs as soon as the script has finished.
- `.ready` can resolve before a font that will be needed has even started loading. The `load` event is a second pass: it fires once every resource the page requested, fonts included, has arrived. `layout` therefore runs at least twice, which is cheap enough, and the second run sees the final metrics.
- Until the first `layout`, `mode` is `"off"` and `view` is `null`, so the scroll handler does nothing for docking or the minimap, and the header logo stays visible as normal.

- The tree drawn with `├──` and `└──` repeats the HTML comment at the top of `index.html`, so view-source and the console tell the same joke.
- **`{KeyWord:Developer}`** is Google Ads Dynamic Keyword Insertion syntax. In ad text, `{KeyWord:Default}` is replaced with the search keyword that triggered the ad. If the keyword does not fit, the default text appears. The capitalisation of `KeyWord` sets the case of the inserted text: `keyword` gives lowercase, `Keyword` capitalises the first word, and `KeyWord` capitalises every word.
- In the console nothing ever replaces it, so the text stays as written. To a marketer who knows the syntax it reads as "the default is showing": whoever opens the console is most likely a developer. The 404 page plays the same joke with `{KeyWord:Page}`.
- `})();` closes and calls the IIFE.

The page follows the system again. Now open the Rendering panel (⋮ → More tools → Rendering), switch "Emulate CSS media feature prefers-color-scheme", and watch `aria-pressed` flip in the Elements panel. That is the `mqDark` change listener at work.

**2. Measure `dist`, then change it.** At the very top of the page (otherwise the name is transformed and the measurement is wrong), repeat what `dockMeasure` computes:

The real `dist` is inside the IIFE, out of the console's reach. **3. Watch `q` while scrolling.** Your console code runs in the global scope, so a `const ease` here does not clash with the one inside the IIFE:

Scroll slowly through the first 150 px. The values move in small steps at first, jump in the middle and creep at the end – the S-curve. To log the script's own `q`, add a logpoint (right-click the gutter → "Add logpoint") on the `hero.classList.toggle("flying", …)` line with `'q', q.toFixed(3)`.

## Key terms

- **IIFE** – immediately invoked function expression: `(() => { … })()`. It creates a private scope, so nothing leaks into or collides with the global scope.
- **Closure** – a function's ongoing access to the variables of the scope it was created in, even after that scope's function has returned. Every handler in this file depends on it.
- **defer** – a script attribute: download in parallel, run once the document has been parsed, in order, before `DOMContentLoaded`.
- **localStorage** – a synchronous string store per origin and per browser profile. It persists across visits, is never sent to the server, and can throw when blocked.
- **dataset** – the `data-*` attributes as properties, with names converted from dashes to camelCase (`data-theme-set` → `dataset.themeSet`).
- **Event loop** – the main thread runs one task at a time. Timers and events queue tasks, and the browser renders between tasks.
- **requestAnimationFrame** – runs a callback right before the next frame is drawn. It is the natural rhythm for visual updates.
- **Forced layout (reflow)** – reading geometry after a change makes the browser compute layout synchronously. Do all writes first, then all reads.
- **Compositing** – the final rendering stage. `transform` and `opacity` can change there without new layout or paint, which makes them cheap to animate.
- **Range** – a stretch of document content. `getClientRects()` returns one rectangle per line of text it covers.
- **Pointer capture** – routes all events from one pointer to one element until release, even when the pointer leaves it.
- **Debounce · throttle** – debounce runs once after a burst of events stops; throttle runs at most once per interval while the burst continues.
